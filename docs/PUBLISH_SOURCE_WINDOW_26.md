# Ограниченное окно последовательного Source commit

Реализовано окно из 64 уже разрешённых scalar/reference операций. Каждая хранит
target/source WHO, собственные typed paths, значение/opcode и исходный токен
commit. Endpoint buffers передаются swap и переиспользуют capacity; второй G
или массив операций на весь проект не создаётся.

flush_constructions применяет результаты строго в порядке входа: канонизация
target, канонизация source при binding, запись G, Source Map, предупреждение.
Ранее записанная цель сохраняет last-write-wins. Read-only endpoint resolution
не читает значения предыдущих assignments: ему нужны типы уже объявленных WHO.

Барьером служат полное окно, объявление объекта/extern, вход/выход namespace,
строка и завершение root. Экспериментальный Source Model также завершает окно
перед собственным непосредственным commit. На ошибке parser сначала применяет
ранее проверенный префикс; ошибка его commit имеет приоритет над более поздней
ошибкой разбора. Счётчик очереди обнуляется перед flush, чтобы внешний error
barrier не воспроизвёл уже применённый префикс повторно. Commit восстанавливает
исходную позицию statement для диагностики, затем возвращает текущий токен.

Настройка `SERVER_ENGINE_SOURCE_CONSTRUCTION_WINDOW_V2=ON` включает 64 операции.
По умолчанию OFF: ёмкость 1 сохраняет немедленное применение тем же commit API.
Большое окно пока экспериментальное, поскольку resolver остаётся
последовательным, а подтверждённого ускорения полного PUBLISH нет. Следующая
часть — отделение входа resolver от binding/cursor, затем worker-контексты.
Нельзя просто запустить нынешний parser параллельно.

## Проверки и измерения

Регрессия с 260 повторными scalar/link операциями и последующими string,
declaration, namespace и EOF проверяет несколько полных окон, финальные значения,
одну актуальную связь и все 259 предупреждений в ожидаемой последовательности.
Сохранена отдельная проверка owned endpoint paths и path-ID order.

Прототип с ёмкостью 64 прошёл frontend regressions, девять интеграционных
сценариев и девять точных сравнений ошибочной диагностики. Последние включают
ошибку после отложенного duplicate warning и duplicate object declaration.
Все 14 full-fixture вызовов с warmup сохранили SHA-256 compiled/runtime файлов
и прошли независимый baseline audit.

Три обычные пары: 1481.547 ms baseline против 1460.360 ms candidate. Отдельные
две stage пары: 1448.105 против 1547.665 ms total, 491.483 против 524.178 ms Source.
Один stage candidate имел общий всплеск, включая lexical. Малые разнонаправленные
серии не подтверждают выигрыш. Дополнительные буферизация и dispatch пока не
окупаются доказанным распараллеливанием, поэтому окно 64 не включено по умолчанию.

Логи, прототип и обе CMake-конфигурации: `build/publish-source-window-26/` и
`build/publish-subsecond-01/`.

Финальная обычная конфигурация OFF прошла 22/22 CTest tests. Отдельная CMake
конфигурация ON прошла frontend regressions, девять интеграционных сценариев и
девять точных сравнений ошибочной диагностики. Полный PUBLISH обеих конфигураций
совпал с эталонными SHA-256 и прошёл независимый audit. Финальные артефакты
оставлены от обычной конфигурации OFF. Измеренный прототип 64 сохранён отдельно
как prototype.exe; повторные финальные проверки скорости не интерпретируются.
