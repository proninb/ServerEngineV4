# Source PUBLISH: использование существующей WHO-модели

Первый срез реализации описан в `PUBLISH_SOURCE_RESOLVER_24.md`: выделены
read-only запросы каталога и граница канонизации endpoint. Окна и workers из
предлагаемой ниже схемы ещё не реализованы.

Следующий срез: `PUBLISH_SOURCE_OWNED_ENDPOINTS_25.md` — независимые локальные
пути operands и канонизация после проверки scalar/link statement.

`PUBLISH_SOURCE_WINDOW_26.md`: реализовано экспериментальное окно ordered commit
на 64 разрешённые операции; по умолчанию commit немедленный. Workers отсутствуют.

`PUBLISH_SOURCE_BOUND_RESOLVER_27.md`: добавлен независимый вход WHO + selectors;
его эквивалентность проверяется на двух native workers. Диспетчер PUBLISH ещё
не передаёт этим workers окна запросов.

## Что уже реализовано

| Представление | Текущее содержимое |
|---|---|
| type_ref::named | slot семантической identity типа |
| base_record::type | identity_ref |
| object_endpoint::object | identity_ref |
| construction_value::object_binding | значение identity_ref |
| graph::identity_locations | прямое отображение WHO в текущее WHERE |

Исторические описания «Current implementation» в
GRAPH_IDENTITY_APPEND_ARCHITECTURE.md для этих полей уже не соответствуют коду.
Мой предыдущий вывод о ранней фиксации физических handles был неточным.

source_parser_v2::resolve_endpoint получает запись через G.find_object(id),
чтобы прочитать тип, но итоговый endpoint сохраняет id. named_type читает
физическую запись для проверки определения/alias, но создаёт G.named(type_id).
Такие локальные чтения WHERE не фиксируют его в семантической ссылке.

## Что действительно сериализует Source

1. string_table::intern и identity_space::resolve назначают ID в порядке входа
   и изменяют общие таблицы.
2. Объявления изменяют объекты G, derived types и extern state. Рост векторов
   несовместим с одновременным чтением другими потоками.
3. G.intern_resolved_endpoint_path изменяет общую таблицу канонических путей.
4. commit_construction немедленно вызывает rebind_resolved_link либо
   add_resolved_initialization, меняя общие массивы и индексы целей.
5. Source Map имеет один active_root; provenance, предупреждения и
   last-write-wins также зависят от порядка.

WHO уже отделён от размещения. Не разделены read-only вычисление и изменение
общих хранилищ. identity_ref сам по себе не делает контейнеры thread-safe.

## Минимальный прототип

Ограниченные окна assignment statements между объявлениями и изменениями scope:

```mermaid
flowchart LR
    A[Binding имён и WHO] --> B[Ограниченное окно]
    B --> C[Параллельный read-only resolver]
    C --> D[Commit в исходном порядке]
    D --> E[Следующее окно или объявление]
```

Диспетчер сохраняет порядок интернирования и текущую видимость object WHO.
Workers получают уже связанные токены. Полный проект заранее не сканируется
для регистрации будущих объявлений. Размер окна ограничивает память.

Worker читает замороженные Header-типы и уже объявленные объекты; разрешает
члены, базы и индексы, проверяет типы и декодирует значения. Результат содержит
object WHO, type_ref, локальные typed endpoint steps и source locations.
Worker не вызывает intern, derive, path interning, Source Map или запись G.
Это временный результат операции, не второй Graph.

Commit в исходном порядке канонизирует пути, применяет результат к WHO,
записывает provenance и предупреждения. Нативные адреса появляются на прежней
границе Runtime. Перед следующим объявлением workers завершены и окно полностью
применено. Никто не читает G одновременно с ростом его контейнеров.

## Условия корректности

- a.x=1; T a; остаётся ошибкой на первом statement; будущий WHO не регистрируется.
- extern T a; a.x=1; T a; сохраняет существующие extern/type правила.
- Из нескольких ошибок выбирается первая по порядку входа, включая ошибки
  lexer/binder: поздняя ошибка диспетчера не обгоняет раннюю ошибку worker.
- Повторные записи и bindings сохраняют last-write-wins и порядок предупреждений.
- Source Map сохраняет порядок, root-local зависимости и физические locations.
- Коллизии имён, inheritance, массивы и ссылки проверяются прежними правилами.
- Fallback выбирается до изменения G; старый parser не повторяет уже выполненную
  проверку resolver на успешном новом пути.
- Приёмка проверяет точные артефакты, диагностику и runtime значения/ссылки.
  Полное время включает подготовку, commit и освобождение окна.

## Порядок реализации

Сначала выделить read-only resolver и проверить его последовательно. Затем
добавить ограниченные окна scalar assignments и reference bindings, после этого
пул workers. Массовые char-array записи рассматриваются отдельно.

Это проект прототипа, не реализованное ускорение. Binding, объявления,
канонизация путей и commit пока остаются последовательными. Наличие N потоков
не обещает N-кратного ускорения. Новый путь должен заменять старую работу;
добавление ещё одного полного прохода может уничтожить выигрыш.

Исполняемый код данным обзором не изменён. Направление — использовать уже
существующий WHO для разделения вычисления и commit, без повторной миграции
identity и без откладывания всех физических чтений до Runtime.
