# SEMANTIC-BIND-01: локальный Header Parser и binding типов

Реализован изолированный прототип. Рабочий PUBLISH не переключён. Проверяется модель локальных символов и разрешения **типовых ссылок**, а не вся семантика Headers и не новый полный PUBLISH.

## Поток данных

```text
Effective preprocessing + context-sensitive token reuse
  → immutable kinds / spellings / array bounds / physical locations
  → parallel local Parser, one task per Header root
  → ordered local-symbol/request assembly + parent forest validation
  → CANONICALIZER-01 exact-key index
  → immutable catalog + parallel type binding
  → existing deterministic WHO numbering
```

Workers не вызывают `identity_space`, `string_table` или G. Они создают собственные ссылки на родителей/владельцев и выражения типов. Binder читает эти результаты, исходные токены повторно не разбирает. Local G отсутствует.

События упорядочены по порядку корней и эффективных токенов, включая развёрнутые includes/macros. Объявление, завершение определения и появление intrinsic alias имеют отдельные события. Каталог может знать о будущем определении, но это не делает его видимым/полным раньше времени. Поиск имени идёт вверх по canonical scopes, отбрасывая объявления после события запроса.

Дополнительно проверен важный случай существующего языка: `struct X; ... X* p ... typedef int X;`. Будущий alias не должен ретроспективно изменять уже разобранный тип указателя. Поведение forward declaration/alias и областей record-family bookkeeping сверено с Header V2, а не выведено из общих правил C++.

Новый Parser получает написания, а не старые WHO/родителей/результаты поиска из trace. Нормализация локального входа теперь измеряется в `local_parse_ms + combine_prepare_ms`.

Эффективный preprocessing пока выполняется старым frontend последовательно и по-прежнему интернирует строки. После его завершения числовые String IDs заменяются spelling views и не передаются workers. Поэтому эксперимент **не доказывает** полный frontend без глобальной string table.

Для каждого прогона независимый Header V2 получает собственные strings/identities/G и заново выполняет preprocessing, без экспериментального token-reuse callback. Сверяются WHO каждого локального символа, нормализованный тип каждого поля, цели базовых типов и полная численность полей по уникальным определениям и G. Номера WHERE, String IDs, Source Map, construction defaults и `compiled.bin` здесь не сравниваются.

В первой разведочной версии стенд независимо разворачивал все includes каждого root. Это породило 20 590 702 запроса, около 17,5 ГБ пиковой памяти и многократную повторную работу. Такой прогон не является измерением рабочего PUBLISH. Исправленный вход повторяет условия допустимости production reuse: пустое macro environment, граница законченного глобального объявления и упорядоченный preflight include/once. Никаких semantic answers при reuse не передаётся. Повторное использование запрещается preprocessing-контекстом внутри namespace или при активных макросах; это отдельно проверено fixtures.

Пять свежих процессов на конфигурацию, плюс один исключённый прогрев. Порядок конфигураций менялся. Ни сборок, ни других тестов одновременно с измерениями не выполнялось. Все строки измерений прошли сверку с oracle.

Медианы отдельных компонент не обязаны складываться в медиану общего времени. Общее время включает также освобождение local outputs и перенос результата стенда, но исключает подготовку токенов, создание pool, oracle/проверку и окончательное уничтожение возвращённых/canonical результатов.

Подготовка входа имеет собственную цену: медианы по 25 измерениям — compose 24,851 мс, physical preparation 152,669 мс, effective preprocessing/capture 162,168 мс, адаптация spelling views 13,106 мс. Эти значения не следует напрямую сопоставлять с фазами PUBLISH: стенд материализует входные токены, а окончательный G вообще не пишет.

Здесь canonicalization обрабатывает только Header symbols. Сравнивать её 1,1 мс с прежними 28 мс CANONICALIZER-01, где присутствовали Header и Source identities/strings, как ускорение одного алгоритма нельзя.

Удерживаемые основные model vectors и modifier arrays занимают 152 732 768 байт (**145,7 MiB**). Это не полный peak temporary memory. Медианный process lifetime PeakWorkingSetSize до запуска oracle составляет около 487–491 MiB в зависимости от числа workers; сюда входят входные токены, подготовка, allocator и временные структуры. Дополнительный расход памяти остаётся архитектурным вопросом; преимущество над существующим PUBLISH по памяти не доказано.

## Проверки

- 270 проверок модели: 1/2/4/8/16 workers и прямой/обратный порядок подачи root tasks. Совпадают WHO, bound types и первая ошибка.
- 120 запусков сверки с независимым Header V2: forward declarations, неполные типы по значению, неизвестные имена, reopened namespaces, временное shadowing, aliases, record families, повторные совместимые/конфликтующие определения, cv/pointers/references/arrays, includes и macro context. Для отрицательных случаев сверяются категория и точные file/offset/length первой ошибки.
- Два CTest эксперимента: 2/2.
- Существующий production CTest: 22/22, без изменения production-кода этим экспериментом.
- Матрицы UnitProXL и scopes: 50 измерений + 10 исключённых прогревов, каждый с oracle.

Raw CSV, stdout/stderr, manifest с hashes исполняемого файла/исходников и статистика лежат в `build/semantic-bind-01/results-unitproxl` и `results-scopes`. Воспроизводимые команды и точные границы метрик — `experiments/semantic-bind-01/README.md`.

## Архитектурный вывод и граница доказанного

Локальные символы и отложенное типовое разрешение работают на реальном Header corpus без глобальных WHO в Parser и без Local G. Согласование идентичностей занимает малую часть текущей модели. Ускорение модели между 1 и 16 workers — около 1,52×; после 4 workers общий выигрыш невелик. Local Parser практически перестаёт ускоряться после 2 workers. По этим данным нельзя приписать причину только allocator, memory bandwidth или дисбалансу roots: для этого нужен отдельный профиль распределения работы.

**SEMANTIC-BIND-01 реализован как первый прототип binding типов; полный Header Binder остаётся недоказанным.** Семантика конструкторов/методов, reference targets внутри constructor operations, member initializers, static objects, access/layout/polymorphism compatibility и вся негативная грамматика не перенесены. Для UnitProXL явно выводится `coverage=partial`. Глобальные проверки выполнены однократно для поддерживаемой проекции, но это не утверждение обо всех семантических проверках Headers.

Приоритет уточнён после [SEMANTIC-BIND-02](SEMANTIC_BIND_02.md): сначала scaling/memory audit и компактность промежуточных записей, затем constructor/reference requests с сохранением порядка и diagnostics. Direct G и Source Binder следует подключать после этой проверки. Пока нет основания обещать полный PUBLISH <1 с или выбирать окончательный scheduler по результату одного ядра.
